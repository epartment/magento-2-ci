# magento-2-ci

Docker images for Magento 2 GitLab CI pipelines, built by GitHub Actions and published to Docker Hub
under `epartment/gitlab-ci` and `epartment/gitlab-ci-composer1`. Each image is a small Dockerfile
plus a build matrix; the matrices are generated by PHP scripts from one shared list of supported PHP,
Node and Deployer versions.

> **Pushing to `master` publishes to Docker Hub.** Every workflow here has
> `push: github.ref == 'refs/heads/master'`, so a merge rebuilds and overwrites the public tags that
> every client pipeline pulls. Pushes to any other branch build the images without publishing them,
> which is the way to test a change.

## Stack

| Component | What it is |
|---|---|
| Docker / BuildKit | `docker/build-push-action@v4` (PHP images) and `@v5` (deployer, bundling) |
| GitHub Actions | three workflows under `.github/workflows/` |
| PHP 8.3 | runs the matrix generators inside the workflow; nothing else |
| Docker Hub | `epartment/gitlab-ci`, `epartment/gitlab-ci-composer1` |
| Platforms | `linux/amd64` and `linux/arm64` (deployer and bundling images; the PHP images are amd64) |

Upstream bases: `php:<version>-cli-<debian>`, `node:<version>-<debian|alpine>`,
`deployphp/deployer:<v7|v8>`, `composer:1` and `composer:2`.

## Getting started

There is nothing to install. Everything builds through Docker.

Build one image locally the way CI does — the build args are not optional, and a missing one produces
an invalid base image name:

```bash
docker build --build-arg PHP_VERSION=8.3 --build-arg OS_RELEASE=bookworm --build-arg ENV_SOURCE_IMAGE=php -t test:php83 .
```

Render a build matrix to see exactly which tags a workflow would produce:

```bash
php .github/workflows/php-matrix/deployer-generator.php
```

To change which versions are built, edit `.github/workflows/php-matrix/constants.php` — that file is
the single source of truth for every matrix.

## Architecture

Five Dockerfiles, three workflows, one shared constants file.

### Code map

| Path | Builds | Base | Published as |
|---|---|---|---|
| `Dockerfile` | PHP CLI with Magento's extensions, Composer 2, PhantomJS deps | `php:<v>-cli-<debian>` | `gitlab-ci:<php>` |
| `node/Dockerfile` | the above plus Node, Yarn, PhantomJS, Puppeteer | `gitlab-ci:<php>` | `gitlab-ci:<php>-node<node>` |
| `composer1/Dockerfile` | swaps Composer 2 for Composer 1 | `gitlab-ci:<php>[-node<node>]` | `gitlab-ci-composer1:...` |
| `deployer/Dockerfile` | Deployer PHAR plus a Node build toolchain | `deployphp/deployer:<v>` | `gitlab-ci:deployer-<v>-node<node>` |
| `bundling/Dockerfile` | Node, Puppeteer with Chrome, gulp, rsync, ssh | `node:<v>-<debian>-slim` | `gitlab-ci:bundling-node<node>` |
| `.github/workflows/imageci.yml` | the three PHP-based images, in a chain | | |
| `.github/workflows/imageci-deployer.yml` | the deployer images | | |
| `.github/workflows/imageci-bundling.yml` | the bundling images | | |
| `.github/workflows/php-matrix/constants.php` | every supported version, in one place | | |
| `.github/workflows/php-matrix/*-generator.php` | one matrix per workflow job | | |
| `.trigger` | a bare hash; changing it forces every workflow to rebuild | | |

### The PHP image chain

`imageci.yml` builds three images in sequence, each `FROM` the previous one via the
`ENV_SOURCE_IMAGE` build arg:

```
php:<v>-cli-<debian>
  └─ php-cli job      (context .)          -> gitlab-ci:<php>
       └─ php-node job     (context node)      -> gitlab-ci:<php>-node<node>
            └─ composer1 job    (context composer1) -> gitlab-ci-composer1:<php>-node<node>
```

Because the jobs are chained with `needs:`, a failure in `php-cli` cancels everything downstream.

The deployer and bundling images are independent of that chain and of each other.

### How the matrices are generated

Each workflow starts with a job that runs a PHP script and writes `matrix=<json>` to `$GITHUB_OUTPUT`;
the build job then consumes it with `fromJson`. The scripts read `constants.php` and differ only in
which lists they cross-multiply:

| Generator | Produces | Marks `latest` when |
|---|---|---|
| `php-generator.php` | one entry per PHP version | `PHP_LATEST` |
| `node-generator.php` | PHP × Node | `PHP_LATEST` and `NODE_LATEST` |
| `full-generator.php` | PHP × Node plus a `node_version: x` row for the Node-less variant | `PHP_LATEST` and `NODE_LATEST` |
| `deployer-generator.php` | Deployer × Node | `DEPLOYER_LATEST` and `DEPLOYER_NODE_LATEST` |
| `bundling-generator.php` | Node only | `BUNDLING_NODE_LATEST` |

The `latest` flag does not create an image. It gates a second `build-push-action` step that pushes the
same build again under a floating alias such as `latest-nodelatest`.

## Images and tags

### PHP with Composer 2 — `epartment/gitlab-ci:<tag>`

General-purpose Magento CI image: PHP with APCu, AMQP, BCMath, Calendar, Exif, GD, Intl, Imagick
(PHP < 8.3), IMAP, MySQLi, PCNTL, PDO MySQL, Redis, SOAP, Sockets, Sodium, XSL, ZIP and Mcrypt
(PHP < 8.2), plus Composer 2. The `-node` variants add Node, NPM, Yarn, PhantomJS, Gulp, Grunt,
Puppeteer, RequireJS, Terser and UglifyJS.

- `latest` — newest PHP, no Node
- `latest-nodelatest` — newest PHP and Node
- `8.3` — PHP 8.3, no Node
- `8.3-node22` — PHP 8.3 with Node 22

### PHP with Composer 1 — `epartment/gitlab-ci-composer1:<tag>`

Identical, with Composer 1 in place of Composer 2. Same tag shapes.

### Deployer — `epartment/gitlab-ci:deployer-<deployer>-node<node>`

For pipelines that deploy with Deployer. Contains the Deployer PHAR at `/bin/dep`, plus Node, npm,
npx, yarn, gulp, grunt, RequireJS and Terser for Magento theme builds. Runs as root.

- `deployer-v8-node22` — Deployer 8 with Node 22
- `deployer-v7-node20` — Deployer 7 with Node 20
- `deployer-latest-nodelatest` — newest supported combination

It deliberately contains **no browser**. Chromium, Puppeteer and penthouse were removed because the
crawling jobs run on the bundling image below; carrying them made every deploy job pull several
hundred megabytes it never used, and forced the image to run as an unprivileged user.

Upstream renamed the Deployer PHAR from `/bin/deployer.phar` to `/bin/dep`, on the `v7` tag as well
as `v8`. Both paths work here: `deployer/Dockerfile` symlinks the old name onto the new one, so a
pipeline calling `php /bin/deployer.phar` keeps working and `dep` works too.

> The bare `deployer-v7` tag is **retired**. It was last built on 2025-01-14, from a two-line ancestor
> of the current `deployer/Dockerfile`, and no workflow produces that tag name any more. It stays on
> Docker Hub so existing pipelines keep working, but it receives no updates — move pinned projects to
> a `deployer-<version>-node<version>` tag.

### JavaScript bundling and critical CSS — `epartment/gitlab-ci:bundling-node<node>`

For the `js` and `critical-css` jobs of a Magento deploy pipeline. Contains Node, npm, a global
Puppeteer with Chrome already installed, gulp-cli, rsync, OpenSSH, git and jq.

- `bundling-node22` — Node 22
- `bundling-nodelatest` — newest supported Node

It contains **no PHP, no Composer, no PhantomJS and no Python**, because those jobs never run
Magento and never install dependencies with Composer. Prefer it over a `<php>-node<node>` tag for
crawling and critical-CSS work.

Leaving PHP out is deliberate and load-bearing. The `js` job has to read the project's
`composer.lock` to find the locked reference of `epartment/javascript-bundling`; doing that in Node
rather than PHP means this image never has to match the Magento project's PHP version. Shipping a
PHP would have made that worse than useless, because `php-cli` resolves to 7.4 on bullseye and 8.2 on
bookworm — so the PHP version would have silently tracked the *Node* version.

Two notes for pipeline authors:

- The image is Debian-based on purpose. `puppeteer browsers install` downloads a glibc build of
  Chrome for Testing, which cannot run on Alpine.
- A browser is installed at build time into `PUPPETEER_CACHE_DIR=/opt/puppeteer`, so a job using this
  image can drop its own `puppeteer browsers install` step and any `PUPPETEER_CACHE_DIR=/tmp`
  override, saving a download on every run.

### Choosing a Node version

If you are unsure which Node version a project needs:

- **Check `package-lock.json`** for the `@types/node` package.
- **If absent**, check the `.env.roll` local stack configuration.
- **If neither exists**, assume Node 14 — it was the only version in the old CI image. Note that no
  such tag is built any more; pick the oldest currently supported version instead.

## Image boundaries & coupling

| Image | Purpose | Verdict |
|---|---|---|
| `gitlab-ci:<php>` | PHP CLI for Magento jobs | **Coherent** |
| `gitlab-ci:<php>-node<node>` | the above plus a full frontend toolchain | **Unfocused** — one image serving "any Magento CI job", which is why unrelated jobs pull 640 MiB |
| `gitlab-ci-composer1:*` | Composer 1 variant | **Coherent**, though the need shrinks every year |
| `gitlab-ci:deployer-*` | Deployer runtime | **Coherent** since the browser stack was removed |
| `gitlab-ci:bundling-*` | crawling and critical CSS | **Coherent** |

**Real coupling.** The three PHP images are chained by `ENV_SOURCE_IMAGE` at build time *and* by
`needs:` at workflow time, so they cannot be built or fixed independently: a change to the root
`Dockerfile` rebuilds all three, and a break in it blocks all three. That coupling is intentional —
Composer 1 and the Node variant are genuinely derived images — but it means the root Dockerfile is
the single riskiest file in this repository.

`deployer/Dockerfile` and `bundling/Dockerfile` share no layers with the chain or with each other.
They duplicate a little Node setup, which is the right trade: the two have different base
distributions for a real reason (musl versus glibc, see the bundling image above).

**What no longer belongs together.** Before the split, the `js` and `critical-css` jobs of the
Deployer pipeline ran on `gitlab-ci:<php>-node<node>` purely because that was the only image with
Puppeteer. They used none of its PHP extensions, none of Composer, and none of PhantomJS. That was
the clearest case of an image being picked for one ingredient and carrying twenty; the
`bundling-node<node>` image exists to end it.

## Environments

There is one environment: GitHub Actions building on `ubuntu-latest`, publishing to Docker Hub.

- Pushes to `master` publish. Everything else builds without pushing, including pull requests.
- Each workflow also runs on a monthly `schedule`, staggered by an hour, to pick up upstream base
  image patches. See [H1](#high) — those schedules are currently not firing.
- Multi-arch builds use QEMU, so an arm64 build is emulated and considerably slower than amd64.
- Layer caching is per tag, in registry-side `*-buildcache` tags.

Two different Docker Hub credential secrets are in use: `imageci.yml` reads `DOCKERHUB_USERNAME` /
`DOCKERHUB_TOKEN`, while the deployer and bundling workflows read `DOCKER_USERNAME` /
`DOCKER_PASSWORD`. Both pairs must exist in the repository settings.

## Common tasks

Render a matrix without pushing anything:

```bash
php .github/workflows/php-matrix/bundling-generator.php
```

Build the deployer image locally, exactly as CI does:

```bash
docker build --build-arg DEPLOYER_VERSION=v8 --build-arg NODE_VERSION=22 --build-arg OS_RELEASE=alpine3.20 -t test:deployer deployer/
```

Build the bundling image locally:

```bash
docker build --build-arg NODE_VERSION=22 --build-arg OS_RELEASE=bookworm -t test:bundling bundling/
```

Check what a published tag actually contains, without pulling it:

```bash
docker buildx imagetools inspect epartment/gitlab-ci:deployer-v7
```

Force a rebuild of everything when no Dockerfile changed — replace the hash in `.trigger`:

```bash
openssl rand -hex 32 > .trigger
```

## Conventions

- **`constants.php` is the only place versions are declared.** Adding a PHP or Node version means
  appending to the relevant array and adding its OS release to the matching map. Nothing else needs
  to change.
- **Branch off `master`; never push a version change straight to it.** A merge publishes.
- **Every image ends with a smoke test.** `deployer/Dockerfile` and `bundling/Dockerfile` finish with
  a `RUN` that executes the tools they claim to ship. A broken copy or symlink then fails the build
  here instead of in a client's pipeline. Keep this when editing them, and extend it when adding a
  tool.
- **Build args have no defaults on purpose.** A missing `PHP_VERSION` or `NODE_VERSION` yields an
  invalid base image name and an immediate failure, which is better than silently building the wrong
  thing. BuildKit's `InvalidDefaultArgInFrom` warning about this is expected.
- **Never change a published tag's meaning.** `8.3-node22` must always be PHP 8.3 with Node 22.
  Floating aliases (`latest`, `latest-nodelatest`, `deployer-latest-nodelatest`) are the only tags
  allowed to move.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| A client pipeline fails with `Could not open input file: /bin/deployer.phar` | The image predates, or was built without, the compatibility symlink; upstream moved the PHAR to `/bin/dep`. | Use a `deployer-<v>-node<n>` tag built from the current Dockerfile, or call `dep` directly. |
| `Could not find Chrome (ver. ...)` at runtime | A global `npm install -g puppeteer` does not download a browser; it only creates the cache folder. | Run `puppeteer browsers install chrome` as its own step, after clearing `PUPPETEER_CACHE_DIR`. |
| Chrome exits immediately in a container | Missing shared libraries, or the sandbox. | Check the library list in `bundling/Dockerfile`; pass `--no-sandbox` when running as root. |
| A Node binary copied into an Alpine image fails to start | The PHP Alpine base does not ship `libstdc++`. | `apk add --no-cache libstdc++`. Do not copy the node image's `/usr/lib` over the base's. |
| Images on Docker Hub are months old although a monthly schedule exists | GitHub disables scheduled workflows after 60 days without repository activity. | Re-enable them in the Actions tab; see [H1](#high). |
| A workflow ran on a branch but published nothing | Intended: `push:` is gated on `refs/heads/master`. | Merge to `master`. |
| `no match for platform in manifest` when pulling | The tag was built amd64-only. | Rebuild with `platforms: linux/amd64,linux/arm64`. |

## Known issues & improvement points

### High

**H1. Scheduled rebuilds have stopped, so every published image is unpatched** — `.github/workflows/*.yml`
`schedule:` blocks

- *What:* All three workflows carry a monthly cron. The last images on Docker Hub are dated
  2025-02-01 for the deployer tags and 2025-06-01 for the PHP tags, and the repository's last commit
  before this branch was 2025-01-15. GitHub disables scheduled workflows automatically after 60 days
  without repository activity.
- *Why it matters:* Every Magento pipeline at the agency pulls these images. They are carrying more
  than a year of unpatched Debian, Alpine, PHP, Node and OpenSSL CVEs, and nothing surfaces that —
  the tags look current because the tag names never change.
- *Suggested fix:* Re-enable the workflows in the Actions tab (a commit alone does not restore a
  disabled schedule), then confirm the next monthly run produces new digests. Consider a cheap
  watchdog: a job that fails if the newest published tag is older than 45 days.

### Medium

**M1. End-of-life PHP and Node versions are still built every month** —
`.github/workflows/php-matrix/constants.php:10`, `:22`

- *What:* `PHP_VERSIONS` includes 7.1 through 8.0 and `NODE_VERSIONS` includes 16, 19 and 21. All are
  past upstream end of life, so their base images receive no security fixes.
- *Why it matters:* Rebuilding them monthly implies they are maintained. They are not: a rebuild
  re-publishes the same unfixed vulnerabilities under a fresh date, which is worse than not
  rebuilding, because it defeats any staleness check.
- *Suggested fix:* Move EOL versions out of the build arrays into a comment recording that their tags
  remain on Docker Hub but are frozen. The existing comment above `PHP_VERSIONS` already describes
  this pattern for older builds.

**M2. `NODE_LATEST` points at an end-of-life Node** —
`.github/workflows/php-matrix/constants.php:21`

- *What:* `NODE_LATEST = '21'` while `NODE_VERSIONS` already contains 22. Node 21 reached end of life
  in June 2024.
- *Why it matters:* `latest-nodelatest`, for both `gitlab-ci` and `gitlab-ci-composer1`, is the tag a
  project picks when it does not want to think about versions — and it currently hands them an EOL
  runtime.
- *Suggested fix:* Set it to `'22'`. The deployer and bundling images already avoid this by tracking
  their own `DEPLOYER_NODE_LATEST` / `BUNDLING_NODE_LATEST`, so changing `NODE_LATEST` only affects
  the two PHP aliases.

**M3. Two different Docker Hub credential secrets** — `.github/workflows/imageci.yml:81`,
`.github/workflows/imageci-deployer.yml:46`

- *What:* One workflow authenticates with `DOCKERHUB_USERNAME` / `DOCKERHUB_TOKEN`, the others with
  `DOCKER_USERNAME` / `DOCKER_PASSWORD`.
- *Why it matters:* Two credentials to rotate, and rotating one silently breaks half the publishing
  while the other half keeps working — a failure that only shows up as tags quietly falling behind.
- *Suggested fix:* Standardise on the token pair and delete the other.

**M4. PhantomJS is still installed in the PHP-Node image** — `node/Dockerfile:20`

- *What:* The image copies a PhantomJS binary from `rollupdev/phantomjs:latest`, an unpinned
  third-party image.
- *Why it matters:* PhantomJS was abandoned in 2018. The dependency is dead weight, and pulling
  `:latest` from an unrelated account on every build is a supply-chain risk that nothing here
  controls.
- *Suggested fix:* Confirm no project still calls `phantomjs`, then remove the copy and the
  `fontconfig`/`libfontconfig` packages that exist only for it.

### Low

**L1. Duplicated apt packages in the root Dockerfile** — `Dockerfile:16`–`:76`

- *What:* Eight packages are listed twice in one `apt-get install`: `libnss3`, `libatk1.0-0`,
  `libc6`, `libcairo2`, `libfontconfig1`, `libgdk-pixbuf2.0-0`, `libglib2.0-0` and `libgtk-3-0`.
- *Why it matters:* Harmless to apt, but the list is already 60 lines and the duplication makes it
  hard to tell what is deliberate.
- *Suggested fix:* Deduplicate and sort.

**L2. `RUN export PATH=...` is a no-op** — `Dockerfile:131`, `composer1/Dockerfile:13`

- *What:* Both files end with `RUN export PATH=$PATH:/usr/bin`. An `export` inside `RUN` affects only
  that layer's shell and is discarded.
- *Suggested fix:* Delete both lines, or convert to `ENV` if the path is genuinely needed.

**L3. `MIGRATE.md` documents tags that no longer exist** — `MIGRATE.md:25`–`:26`

- *What:* It tells readers to use `7.4-node10` and `8.1-node14`. Node 10 and 14 are not in
  `NODE_VERSIONS`, so neither tag is built any more.
- *Suggested fix:* Update the examples to currently built combinations, or retire the document — the
  migration it describes happened in 2023.

**L4. The `.trigger` mechanism is undocumented in the file itself** — `.trigger`

- *What:* The file holds a bare 64-character hash and is listed in every workflow's `paths:` filter,
  so changing it forces a rebuild. Nothing says so.
- *Suggested fix:* This README now explains it under [Common tasks](#common-tasks); a one-line
  comment is not possible in a file matched by an exact-path trigger, so leave the file alone.

## Audited and clean

Checked during this pass and found correct.

- **The bundling image builds, and Chrome actually starts in it.** The `node22` (bookworm) and
  `node18` (bullseye) variants were built locally for `linux/amd64`, and verified with a real
  `puppeteer.launch()`, which reported `Chrome/152.0.7977.75`, alongside node, gulp, rsync, git and
  jq. It measures 329 MiB compressed (853 MiB on disk) against 640 MiB compressed for the
  `8.3-node22` image these jobs use today.
- **The image contains no PHP, and nothing needs it to.** `command -v php` returns nothing. The one
  task PHP performed — reading the consuming project's `composer.lock` to find the locked reference
  of `epartment/javascript-bundling` — was rewritten in Node and tested against a real
  `composer.lock`, returning the expected source URL and 40-character reference with exit `0`.
  This matters more than it looks: `php-cli` resolves to 7.4 on bullseye and 8.2 on bookworm, so a
  PHP in this image would have silently tracked the Node version rather than the project's.
- **The deployer image builds and works for both Deployer majors.** `deployer-v8-node22` and
  `deployer-v7-node20` were built locally for `linux/amd64` and verified to report Deployer 8.0.5 and
  7.5.12 respectively, via both `dep --version` and `php /bin/deployer.phar --version`, with
  `id -un` returning `root`.
- **Dropping the wholesale `/usr/lib` copy did not break Node.** The narrow copy plus
  `apk add libstdc++` yields a working `node`, `npm` and `yarn` in both variants, confirmed by the
  in-build smoke test.
- **The PHP image matrices are unchanged by the `constants.php` edits.** `php-generator.php`,
  `node-generator.php` and `full-generator.php` produce byte-identical output before and after,
  compared against `master`.
- **Yarn really is present in the Alpine Node images.** `node:22-alpine3.20` sets `YARN_VERSION`, so
  the `mv /opt/yarn* /opt/yarn` and `/opt` copy that `deployer/Dockerfile` relies on are sound.
- **`ARG` before `FROM` is used correctly.** The three build args are referenced only in `FROM`
  lines, which is the one place a pre-`FROM` `ARG` is visible without redeclaration.
- **Publishing is correctly gated.** Every `build-push-action` in every workflow has
  `push: ${{ github.ref == 'refs/heads/master' && !env.ACT }}`, so branch and pull-request builds
  cannot overwrite a public tag.
